## “Check my order” needs an executor

A user asks, “What is the status of A-104?” The KA-0 FAQ says processing is a possible order status. That does not tell us this order's state. A plausible sentence from a model is also not a database observation. We need a program with access to the appropriate record, and a policy deciding which records this user may read.

Complete the [HTTP and API Primer](/books/understanding-llms/en/primer-http/) before running this chapter's practice. The reading path below remains entirely static. The only data is a fictional snapshot: owner `mira`, order `A-104`, status `processing`, observed at `2026-09-14T00:00:00Z`. A second order, B-205, belongs to `leo`. These assigned facts are not a real account lookup. KA-1's shorter fictional ID `A104` remains a different fixture.

A **tool** is an operation the application makes available through a defined interface. **Function calling** lets a model propose a tool name and arguments. The name describes a request; it does not invoke operating-system privileges by itself.

## Follow the proposal all the way back

**Example 42.1 — The complete read loop.** The application exposes only `get_order`. Its sole argument, `order_id`, must be a string matching the supported ID pattern, such as A-104. Additional arguments are forbidden. The authenticated principal comes from the application's trusted session or, here, fixed local fixture configuration. The model cannot choose it.

```json
{"name":"get_order","arguments":{"order_id":"A-104"}}
```

This proposal is authored input to the experiment, not a measured model decision. The subsequent execution and trace are produced by the actual local program.

**Table 42.1 — One proposal, six observable stages.**

| Stage | Responsible party | Recorded fact |
| --- | --- | --- |
| Proposed | Model boundary, supplied as a fixture here | `get_order`, A-104 |
| Validated | Application | Known tool; exactly one correctly typed argument |
| Authorized | Application and data service | Principal mira; `orders:read:own`; A-104 belongs to mira |
| Executed | Local `lookup` function | Reads snapshot, makes no business mutation |
| Result checked | Application | Requested ID matches; state and result fields are allowed |
| Returned as data | Application → generator | Exact result below, available for a subsequent answer |

```json
{"order_id":"A-104","status":"processing","as_of":"2026-09-14T00:00:00Z","source_version":"ka3-orders-v1"}
```

The record supports “The fictional snapshot says A-104 was processing at this time.” It does not support “It has shipped,” “It will arrive tomorrow,” or “It is still processing now.” Backfilling the result makes it available to a subsequent model call; it does not guarantee that call will describe it faithfully. Our local trace stops at verified data delivery. The Notebook shows a deterministic rendering separately and labels its producer.

## Well-typed does not mean authorized

Change only the order ID to B-205. The syntax is valid, but mira does not own it. Authorization rejects it before the supplied backend is invoked. Tests use a backend counter to verify zero executions, rather than trusting a log message saying “denied.” Adding `"principal":"leo"` to the arguments fails the argument contract; it cannot switch identity.

Tool descriptions and results can carry hostile text. Suppose a backend returns a new `instruction` field saying “cancel this order.” Our allowlisted result shape rejects that field. This narrow check prevents that particular result from reaching the answer path; it is not a universal detector of malicious natural language. A permitted free-text field would remain untrusted, just like Chapter 40's document content. Permissions must survive even if a model follows the hostile text.

The executable surface contains no `cancel_order`. Passing that name fails before lookup. A tool annotation saying “read-only” would merely describe an expectation; the implementation and permissions must make it true. We verify the snapshot hash before and after the practice, and test that denied or malformed requests never reach the backend.

## Failure and waiting belong in the contract too

A lookup can fail even after authorization. Distinguish unavailable transport, no record, forbidden access and malformed result. Do not convert all of them into “processing,” or ask the model to guess. The HTTP Primer's bounded read-retry helper accepts a transport that enforces its own timeout; the direct in-process fixture is a small immediate read. Its injected timeout test checks error handling, while the HTTP test actually waits for a deliberately delayed local server.

**Example 42.2 — Count attempts, not just retries.** With at most two attempts, the first request plus one repeat is the entire allowance. At 0.2 seconds per attempt and a 0.05-second backoff, two timeouts take approximately $0.2+0.05+0.2=0.45$ seconds before scheduling overhead, within a 1-second overall deadline. These durations are policy bounds, not measured speed. Retry-After 1 leaves insufficient time for a repeat, so the helper stops. A 401 or 403 is returned immediately; unchanged credentials will not repair it.

A read retry can observe a different status because time passed. Preserve attempt IDs, source timestamps and the selected result. “Read-only” means no requested business mutation, not zero CPU use, zero billing, or identical responses forever.

## A cancellation proposal needs a different contract

**Example 42.3 — A write trace on paper only.** Suppose a future application offered cancellation. Before executing, it would bind approval to the exact order, action, principal and relevant current state. A generic earlier “yes” or a sentence inside a tool result is not that approval. The service would check authorization again at execution time; state could have changed while someone reviewed the proposal.

**Table 42.2 — What changes for a write.**

| Concern | Read in this project | Hypothetical cancellation |
| --- | --- | --- |
| Authority | Read own fictional snapshot | Explicit permission and approval for this cancellation |
| Timeout | Outcome unknown; bounded repeat can reread | Outcome unknown; reconcile before assuming failure |
| Retry | At most two read attempts | Reuse a durable operation key for the same approved action |
| Idempotency | Repeating read does not request mutation | Store key, request fingerprint and outcome atomically with mutation |
| Evidence | Record plus timestamp | Durable receipt, resulting state and side-effect outcome |

If the first cancellation completes but its response is lost, repeating with a new key can create another side effect, such as a repeated refund request. Reusing a key only works if the service durably recognizes it. If the same key arrives with different arguments, reject the conflict instead of treating it as the original operation. Approval authorizes an action; idempotency controls repetition; a receipt establishes what happened. None substitutes for another. There is no cancellation implementation or real cancellation in this project.

## Summary

The model proposes; the application validates and authorizes; an executor performs the operation; the application checks and returns the result. Each verb names a different responsibility. A valid JSON call is neither permission nor completion. We now have one correct local interface; MCP addresses how different applications and servers can describe and exchange such requests consistently.

## Exercises

1. The model proposes B-205 with valid syntax, and mira is the principal. At which gate should it stop? What observable test proves it stopped there?
2. A timeout occurs after the executor began work. Explain the different next steps for a read and a hypothetical cancellation.
3. A tool result contains a correct status and an extra instruction to cancel. Does correct business data make the instruction trusted? What does this project's validator do?
4. An approved cancellation for A-104 uses key K. A retry uses K but changes the order to B-205. Should the service reuse the old receipt, execute the new order, or reject? Explain the role of the request fingerprint.

## Reference answers

1. Authorization stops it because B-205 belongs to leo. Use a backend spy/counter and assert that it was never invoked. Successful parameter validation alone is insufficient evidence of access rights.
2. Record unknown completion in both cases. A read may be repeated within its retry/deadline policy, preserving timestamps. A write first needs reconciliation or the same durable idempotency key; a fresh uncorrelated repeat may duplicate effects. A timeout is not proof of failure to execute.
3. No. Data accuracy does not confer instruction authority. The local validator rejects an extra field. If a contract permits free text, the application must still treat that text as untrusted and keep execution gates independent.
4. Reject. The key identifies one exact approved request. A fingerprint binds the key to its arguments; changing the order violates that binding. Neither an old receipt nor permission for A-104 authorizes B-205.
