## A selection report is allowed to select neither

[Chapter 32](../ch-32/) fixed the Knowledge Assistant's success criteria before running candidates. We can now answer a concrete question: do either of the two available CPU configurations meet that contract? The answer is no. One configuration handles two English current-amount cases better, and both run quickly on these tiny inputs, but neither meets the bilingual fact, history, status and approval requirements.

That is a completed selection decision, not a missing winner. A report that must name a winner regardless of the gates would reward the least inadequate candidate as though it were adequate. KA-1 instead preserves the evidence, identifies what each configuration can support, and states what would have to change before another comparison.

The report uses vendor-neutral labels A and B for the local comparison. A is MG-2's validation-selected step-50 checkpoint; B is the same architecture at step 600. These are genuinely different trained parameter configurations, not fabricated large-model benchmarks. A lower validation loss previously selected A, while B had lower training loss. Neither loss substitutes for the application contract.

## Identify exactly what was compared

**Example 33.1 — The measured comparison record.** The run was recorded on 2026-09-13 under `ka1-contract-v1`, whose cases and input hashes were frozen before execution. Both candidates use the existing 13,875-parameter Mini GPT, context length 64, the same byte-BPE tokenizer, float64 CPU arithmetic, and one thread. No checkpoint was retrained or converted. Parameter tensors contain 111,000 bytes per model: $13{,}875\times8$. This excludes Python, PyTorch, activations and file-container overhead; it is not process peak memory.

The environment was Python 3.12.10, PyTorch 2.7.0 and macOS 26.5.2 on arm64, installed in a fresh temporary CPU environment using the repository's pinned dependencies. The primary greedy policy and the temperature-0.7/top-k-5 stress policy each ran three seeds on six cases in each language. There are $2\times2\times3\times6\times2=144$ attempts: candidates, policies, repeats, cases, languages. All attempts remain in the record.

Loading was outside timing; each candidate received two warmup calls. Timing covers the whole existing generation function, including trace collection and byte decoding. It recomputes the full prefix and has no KV cache or network. The latency measurements therefore cannot establish production TTFT, TPOT, concurrency or server availability. A very short wrong answer may complete especially quickly.

| --- | ---: | ---: | ---: | --- |
| A, English | 0 | 6 | 2 | 0.718 / 0.983 |

Eighteen timings do not establish a reliable production tail. A's six semantic passes are the same two cases repeated, not six distinct successes. All primary outputs are valid UTF-8; their poor Chinese performance is a content problem, not merely byte decoding.

## Compare hard constraints before weighted preferences

**Table 33.4 — Evidence and remaining obligations for the local candidates**

| Dimension | A and B evidence | Decision consequence |
| --- | --- | --- |
| Ability and language | Table 33.1–33.3; A only 2/6 English robust cases, both 0/6 Chinese | Both fail the quality gate |
| Latency | Small warm CPU calls below the diagnostic 1,000 ms p95 gate | Speed does not repair incorrect answers; no service SLO proven |
| Cost | No paid inference calls; tensor storage counted | Hardware, electricity, idle capacity and maintenance cost unmeasured |
| Privacy | Local runner loads repository data/weights and makes no service requests | Prompt egress avoided in this experiment; deployed logging/access still needs review |
| License | Original book data/checkpoints CC BY-SA 4.0; original code Apache-2.0 | Preserve per-asset terms; do not label the whole package with one license |
| Availability | Runs with retained local files in the tested CPU environment | No API quota dependency; no uptime or multi-user resilience test |
| Maintenance | Small inspectable model, fixed tokenizer, explicit tests and hashes | Owners still need dependency updates, data versions, recovery and monitoring |

Some dimensions are gates. A requirement to keep a particular dataset local can eliminate an external route before quality testing. An unmet current-policy or approval rule eliminates these local candidates despite low latency. Weighted preferences are useful only among candidates that satisfy the hard constraints. Otherwise, cheapness can mathematically “compensate” for behavior the application explicitly forbids.

If two feasible candidates trade latency against operating effort, record why the intended workload values one more. If A is no worse on every measured preference and better on at least one, it dominates B on those measurements; missing privacy or language evidence still cannot be assumed favorable. A leaderboard's task mix rarely equals the application's full constraint set.

## Price the workload rather than the model name

**Example 33.2 — An assigned monthly cost comparison.** Suppose two hypothetical candidates have already passed the same quality and privacy gates. The API costs USD 2 per million billed input tokens and USD 10 per million billed output tokens. Each request is assigned 1,000 billed input and 200 billed output tokens, with no cache, tools, retries or discounts. Its cost is $1000\times2/10^6+200\times10/10^6=0.004$ dollars per request.

A hypothetical local service costs 20 dollars per month in fixed capacity plus 0.001 dollars per request in variable cost. At 1,000 requests, API cost is 4 dollars and local cost is 21. At 10,000, API cost is 40 and local cost is 30. Let R be monthly request count. Equality requires

$$
0.004R=20+0.001R,\qquad R=20/0.003\approx6{,}666.67.
$$

The left side is API dollars; the right side is local fixed plus variable dollars. For whole requests, the local estimate becomes cheaper from 6,667 per month under these assumptions. It does not establish that the local machine can serve that traffic at the required latency, or that staff time is included. Failed attempts and retries belong in cost per successful request. Different tokenizers also produce different billable counts for the same text; do not copy Mini GPT's token count into another provider's bill.

This example is deliberately vendor-neutral. Actual quoted prices, product versions and license terms belong in a dated verification layer, separate from the stable decision method.

Neither was executed under KA-1, and neither can be chosen on the basis of the CPU results above. They illustrate what to verify before an optional future experiment.

The API identity and rates come from its [model specifications](https://platform.claude.com/docs/en/models/haiku-4-5/overview) and [official pricing table](https://platform.claude.com/docs/en/about-claude/pricing). At those base rates, an assigned 1,000-input/200-output request would cost 0.002 dollars before other charges. This is an estimate, not an invoice. Listed access is subject to the [supported-region policy](https://www.anthropic.com/supported-countries); mainland China is absent from the inspected commercial API list. The example is not a proposal to bypass access conditions.

The provider's [commercial terms](https://www.anthropic.com/legal/commercial-terms) and [organization-retention policy](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data) answer different questions from price. A no-training statement does not mean zero storage. The inspected standard API retention rule has a 30-day timeframe with service/agreement, enforcement and legal exceptions, and longer rules for some flagged or feedback data. A particular organization must verify its applicable contract and data path; this book does not approve submission of private records.

For the local example, read the [specific model card](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct), [config](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blob/main/config.json) and [actual license](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blame/main/LICENSE). Its family introduction mentions longer contexts, but this model's own limit is 32,768. The config's last-change revision begins `eaa56b5`; the license was introduced at `f0ef055`. The record retains full file-change hashes and does not misrepresent them as a pin of the entire current repository. Before a real run, pin the complete weight/tokenizer/config revision and tested engine as well.

**Open weight** means weights are made available under some terms; the term alone says nothing complete about freedoms, training code or data information. The [OSI Open Source AI Definition 1.0](https://opensource.org/ai/open-source-ai-definition) identifies additional requirements, including the preferred form for modification. An Apache-licensed weight release is useful license evidence, not automatic proof that every system component satisfies that definition. Conversely, local execution can avoid an external prompt service while still leaking through application logs or integrations if those are designed poorly. Architecture, access, licensing and operations are separate axes.

## KA-1 decision and the next question

The completed report rejects A and B for the stated assistant use, retains A for the existing teaching role, and preserves both checkpoints and every failure for follow-up. Reconsideration requires a new frozen comparison with an appropriate candidate, unchanged or explicitly versioned task criteria, full language coverage and new evidence for any previously missing requirement. No API/GPU experiment, independent human-panel validation, production load test or deployment is claimed.

The evidence package contains the contract, pre-run freeze, model/tokenizer/data/code hashes, 144 raw attempts, adjudication reasons, lexical same-set comparison and this dated decision. The accompanying English engineering report provides commands and machine-readable file paths. Core reading requires neither running code nor purchasing access; the visible tables suffice to audit why these candidates fail.

At the end of this part, follow one request across all layers. Data provenance and mixture affect what training can learn; parameters, tokens and compute constrain the run; components and architecture shape its state; generation chooses outputs; inference and serving consume resources; evaluation determines whether the result is acceptable. Improving one link does not certify the rest. The next question is therefore motivated by evidence: why does a base model trained to continue text still need separate teaching to follow instructions and assist a user? Chapter 34 begins there.

## Summary

Choose against a fixed scenario, not a product menu. Record real identities, complete outputs, repeated conditions and dates; separate measurements, assigned traces, estimates and provider claims. Apply hard gates before preferences and cost calculations. KA-1 is complete when its evidence supports a decision, including a defensible rejection of every measured candidate.

## Reference answers

1. Two English cases pass on each of three repeats; repeat identity does not add task coverage. Both current questions require 750, while the historical question explicitly requires 600. A content string's correctness depends on the evidence and question, not the digits alone.
2. At 5,000 requests, API cost is 20 dollars and local cost is 25. With 400 output tokens, API cost becomes $0.002+0.004=0.006$ dollars per request. Equality is $0.006R=20+0.001R$, so break-even is 4,000 requests. The unchanged local variable cost is an assumption, not a measured fact about longer answers.
3. It confuses an author-assigned runtime scenario with a measured checkpoint run. A's actual recorded quantity is complete warm CPU generation-call time, including tracing and decoding; it is not streaming TTFT. Keep both records with their own labels.
4. Investigate data filtering/version governance; cache validity in the engine; generation/model behavior and stop records; evaluator format-versus-semantic rules; and server scheduling/capacity. These are starting hypotheses, to be tested rather than automatic diagnoses of every case.
5. Active count does not reveal resident total weights, cache or workspace. “Open” lacks an inspected license and modification materials. “Chat” can describe a wrapper; the architecture and context representation are still unspecified. Long-context capacity does not prove correct use of the new 750-yuan evidence.
6. Examples include realistic document lengths and citations, genuinely unused representative bilingual cases, independent human review, sustained load/tail latency, privacy/access controls, and recovery/operational ownership. Any four with a reason are appropriate. Twelve public compact diagnostics provide a narrow check, not coverage of all user distributions and deployment conditions.
